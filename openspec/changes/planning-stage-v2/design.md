# Design — planning-stage-v2

> 2026-07-02 명섭 디스코드 탐색 세션 캡처. 5개 결정 + 근거 + 기각안 + 구현 방향.
> 이 문서는 후속 구현 change들의 단일 진실원. 구현은 여기서 예광탄으로 좁혀 분리한다.

## 용어 정리 (혼동 방지 — 대화에서 3턴 겉돈 지점)

- **뼈대 ≠ capability 키.** 뼈대 = 상주 기획 문서 레이어(`docs/`: PRD·features·user-flow·spec). capability = 그 문서들을 기능 단위로 조직하는 **키**. (참고: 사용자가 "뼈대=기능정보?→연관정보?→openspec문서?"로 좁혀오며 이 구분이 드러남)
- **spec.md 두 종류 주의**: standing `docs/spec.md`(audit 기준, 이 change 대상) ≠ change의 `openspec/changes/<c>/specs/<cap>/spec.md`(변경 산출물). flowforge UI의 "기능명세서(spec)" 탭은 후자다.

## 결정 1 — 안2: spec.md = 숨은 빌드산출물

### 무엇
사람은 `docs/planning/features.md`·`user-flow.md`만 편집. `docs/spec.md`(뼈대=capability+assert/invariant/metric)는 features.md에서 **자동생성**되는 빌드산출물로 강등. 화면에 문서로 안 뜨고, audit만 읽는다.

### 왜 (명섭 원칙)
"뼈대를 별도 openspec 문서로 따로 두지 말고 기능명세·유저플로우에 연관시켜라." → 사람 인지에서 뼈대 문서를 소멸시킨다.

### 기각안
- **안1(spec.md 완전 삭제, assert를 features.md에 인라인)**: 원칙 물리+인지 완전 부합이나 audit 파서 재작성·기능명세 무거워짐 = 공사 큼. → 기각. (인터랙티브 목업 비교 후 명섭이 안2 선택)

### 현재 상태 격차 (코드 조사, 파일:라인)
| 항목 | 판정 | 근거 |
|---|---|---|
| spec.md 생성 | 거의 됨 | openspec-plan `SKILL.md:197-254`가 features.md→spec.md LLM 자동변환. 사람 편집 절차 없음 |
| flowforge 노출 | 이미 안 함 | `web/App.tsx:77,541-546` 탭=PRD/features/flow만. spec.md는 `projects.ts:64` capability 데이터로만 소비 |
| audit 입력 | 이미 됨 | `audit_match.py:424` `--spec` 필수. features.md 직접 안 읽음 |
| 손편집 방지 | 격차 | spec.md에 AUTO-GENERATED 마커 없음. 단 `api-spec.md`가 `AUTO-GENERATED/audit:skip`+bodyhash 감지 패턴 보유 → 이식 |

### 구현 방향 (딱 3가지, 공사 작음)
1. openspec-plan 스킬 문구: spec.md를 "features.md 재생성 빌드산출물, 손대지 마라"로 강등(멱등 "보존" 규칙과 충돌하는 부분 정리).
2. spec.md 상단 AUTO-GENERATED 마커 + 손편집 감지·재생성 로직(api-spec.md 패턴 재사용) = **유일한 실코딩**.
3. flowforge: 없음(현상 유지가 곧 안2).

### 리스크
audit 기준(spec.md) 인접 = 비가역. verify로 검증 후 착수. 손편집 감지가 진짜 생성물을 덮는 오작동 없게 무력화 프로브로 방어 커버 검증.

## 결정 2 — 화면(페이지)을 1급 공유 노드로 + 상세기능 N:M

### 무엇
화면(페이지) 엔티티를 명세에 **1급**으로 두고, 상세기능을 화면에 N:M으로 연결한다. 유저플로우·와이어·IA 세 뷰가 **같은 화면 노드를 공유**한다.

```
   현재 (뷰별 추론)                 목표 (화면 1급 공유)
   ─────────────────                ──────────────────
   features.md ─┐                   features.md
                ├→ 각 뷰가            상세기능 ─┐
   user-flow ───┤  화면을 spec에서    기능 ─────┼→ 화면(페이지) ←─ 유저플로우
                │  따로 추론 →        요구사항 ─┘   1급 노드      ←─ 와이어
   → 뷰 간 화면 목록 어긋남 위험         (N:M 연결)   └─────────── ←─ IA
                                     → 세 뷰 자동 정합
```

### 왜 (manyfast 벤치마킹)
manyfast는 5문서가 아니라 4종 아이템(요구사항·기능·상세기능·**페이지메뉴**)의 여러 뷰. "페이지메뉴"가 IA·유저플로우·와이어에 공유돼 뷰 정합이 자동(출처: docs.manyfast.io plan/ia.md, wireframe.md, concept/interface/item.md). 우리는 화면을 spec THEN에서 추론만 해 뷰 간 어긋남 가능.

### 기각/대안
- **상세기능 leaf가 화면에 1:1**: manyfast에도 그런 규칙 없음(한 화면에 상세기능 여러 개, 자유 연결). → N:M 채택.
- **capability 키 문자매칭만 유지**: 화면 축 없이는 뷰 정합 불가. → 화면 1급화 추가.

### 구현 방향
- features.md/user-flow 스키마에 "화면(페이지)" 1급 노드 + "화면↔상세기능" 명시 연결 도입.
- flowforge 세 뷰가 그 공유 화면 노드를 렌더. specParser/flowBinder는 골든테스트 고정이라 그 위 레이어로.

### 관계 (중요)
**이 결정이 결정 4(단일그래프)의 첫 증분이다.** 페이지메뉴 = 4종 아이템의 하나를 1급으로 올리는 것.

## 결정 3 — 유저플로우 에지케이스 자동 분기

### 무엇
spec의 예외 신호(`invariant: safe-4xx`, 에러 THEN)에서 예외 경로를 유저플로우 **분기**로 자동 생성.

```
   happy (실선)                  에지케이스 (점선, 자동)
   ───────────                   ──────────────────────
   [입력] → [검증] → [성공] → [홈]
                │
                └╌╌▶ [비번틀림] ╌╌▶ [에러] ╌╌▶ [재입력]
                └╌╌▶ [계정없음] ╌╌▶ [가입유도]
                └╌╌▶ [safe-4xx] ╌╌▶ [에러표시]
```

### 왜
manyfast는 안 함(예외를 산문 export로 뺌) = **우리가 앞서가는 차별점**. 재료 있음: spec에 이미 safe-4xx·에러 THEN 존재. "자동 에지케이스가 manyfast 기능"이란 소문은 홍보글 1건발 오류로 폐기됨(공식docs·독립리뷰 반박).

### 함정 3개 (착수 시 반드시)
1. **신호 정의**: 1단계=spec 근거만(결정론, 거짓 없음). 2단계=AI 추론 제안(풍부하나 거짓 위험 → 옵션·후속).
2. **노이즈 방지**: 화면마다 네트워크·타임아웃·권한 다 그리면 그래프 폭발. 공통 예외는 접고 화면 고유 예외만 펼침.
3. **시각 구분**: happy=실선, 에지=점선 분기. 이게 "유저플로우→프로세스" 격상의 첫 발.

### 예광탄
1단계(spec safe-4xx/에러 THEN → 점선 분기, 결정론)만. AI 추론·스윔레인·백엔드 스텝은 후속.

## 결정 4 — 뷰-데이터 단일그래프 = 종착지 (빅뱅 X)

### 무엇
궁극적으로 아이템 4종(요구사항·기능·상세기능·페이지)을 한 그래프로 통합(manyfast 사상). 현재는 features.md/user-flow.md/prd.md 파일별 분리 + capability 키 링크.

### 왜 "종착지"이지 지금 하는 게 아닌가
- 전면 재작성 = specParser/flowBinder 골든테스트, 이미 archive된 change 다수, audit 호환 전부 걸림 = 큰 리스크.
- **결정 2(화면 1급화)가 이 아키텍처의 첫 조각.** 2번을 증분으로 반복하면 자연히 4번 쪽으로 수렴.
- → 빅뱅 재작성 금지. 방향으로만 두고 증분 도달.

### 기각안
- **지금 단일그래프로 갈아엎기**: 리스크 큼, 예광탄 원칙 위반. → 기각.

---

## 결정 5 — 경량 아이템 메모

### 무엇
아이템(화면·기능)별 한 줄 메모(설계 이유·TODO·나에게 던지는 질문).

### 왜 경량인가
협업 코멘트(resolve/reply/멘션)는 개인용 도구엔 오버킬. AI 제안 승인루프(6a/6b)와는 **별개 축**(사람이 직접 남기는 메모).

### 기각안
- **manyfast식 협업 코멘트 스레드(resolve/thread)**: 혼자 쓰는 도구엔 과함. → 경량 메모로 축소.

## 구현 로드맵 (점진 — 빅뱅 금지)

```
[이 change: explore 캡처]  ← 지금
        │
        ▼
[예광탄 1] 안2 spec.md 강등 (결정1)      ← 공사 작음, audit 인접 verify
        │
        ▼
[예광탄 2] 화면 1급 노드 + N:M (결정2)   ← 결정4의 첫 증분
        │
        ▼
[예광탄 3] 에지케이스 점선 분기 1단계 (결정3)
        │
        ▼
[후속] 경량 메모(결정5) · 단일그래프 증분 도달(결정4) · AI추론/프로세스 격상
```

각 예광탄 = 독립 change로 propose→apply→verify→review→archive. openspec 도그푸딩.
